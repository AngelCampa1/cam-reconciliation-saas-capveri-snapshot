# E&O Warranty Infrastructure Design

**Date:** 2026-02-24
**Feature:** $50,000 Deterministic Billing E&O Warranty

---

## Goal

Provide a legally credible, insurable $50,000 warranty covering algorithmic calculation
errors in CapVeri's deterministic billing engine. The warranty is a key sales
differentiator that lets landlords present risk-reversal to CFOs and enables the company
to obtain E&O insurance.

---

## Core Problem

To make a software warranty credible, we need to answer three questions:

1. **Which code produced this result?** — Git SHA embedded in every trace
2. **Has the result been altered since it was produced?** — SHA-256 trace checksum at finalization
3. **Is the input data correct?** — Explicit user attestation gate before issuance

Without these three elements, any warranty claim could be disputed as either a code error
or a data entry error, making the warranty unenforceable.

---

## Architecture

### Calculation Provenance

Two fields are added to `reconciliation_snapshots`:

- `engine_version VARCHAR(40)` — Git SHA of the calculation engine at the time the
  snapshot was finalized. Populated by `get_engine_version()` in
  `backend/app/core/versioning.py`, which reads `git rev-parse HEAD` once and caches
  the result for the process lifetime.

- `trace_checksum VARCHAR(64)` — SHA-256 of the serialized `CalculationTrace` JSON
  (sorted keys, deterministic). Computed by `compute_trace_checksum()` in
  `backend/app/services/calculation/trace_persistence.py` and written alongside the
  trace at snapshot finalization time.

These two fields appear verbatim in the issued PDF certificate, enabling independent
verification that neither the code version nor the calculation results were modified
after the fact.

### Error Attribution

A new `ErrorSource` enum is added to `backend/app/schemas/errors.py`:

- `user_data` — Errors caused by inaccurate input data (validation, bad values)
- `software_logic` — Errors in the calculation engine itself
- `system_infrastructure` — Unexpected server errors

The `error_source` field is populated automatically by the exception handlers in
`backend/app/exceptions/handlers.py`. This classification is essential for warranty
claims: the warranty only covers `software_logic` errors.

### Warranty Certificate Lifecycle

Certificates are first-class entities in the `warranty_certificates` table with a
strict state machine:

```
pending_attestation → eligible → issued → voided
```

**Transitions:**
- `pending_attestation`: Created automatically when user requests a certificate for an
  eligible snapshot. Waiting for data attestation.
- `eligible`: User has confirmed all ingested input data is accurate. Certificate can
  now be issued.
- `issued`: Certificate number assigned (WAR-YYYY-NNNNN format), PDF generated with
  SHA-256 checksum, attestation + provenance data frozen in PDF.
- `voided`: Issued certificate cancelled with a required reason (e.g., lease terminated).

**Eligibility prerequisites** (checked before creation and before issue):
1. Snapshot must be in `finalized` status
2. Snapshot must have `engine_version` and `trace_checksum` populated
3. No existing non-voided certificate for the same snapshot

### Data Attestation Gate

Before a certificate can be issued, the responsible user must explicitly confirm that
all ingested data (leases, invoices, GL entries) has been independently verified for
accuracy. This is the legal dividing line between software bugs (covered) and data
entry errors (not covered). The attestation is recorded with:

- `data_attested_at` timestamp
- `data_attested_by` user UUID

### PDF Certificate

Generated by `WarrantyCertificateGenerator` using ReportLab. Contains:
- Certificate number, issue date, reconciliation period
- Property and tenant information
- Engine version (Git SHA) and trace checksum — printed verbatim for verification
- Attestation record (who attested and when)
- Full warranty terms and limitations (up to $50K, algorithmic errors only, 12-month
  dispute window, adjudicated disputes only)

The PDF bytes are SHA-256 checksummed and stored as `certificate_pdf_checksum` to
detect document tampering.

## Key Design Decisions

### Why Git SHA instead of semantic version?

Semantic versions require manual bumping and can be applied to different commits.
A Git SHA is immutable and uniquely identifies the exact code that produced a result.

### Why SHA-256 of the trace instead of the snapshot?

The trace contains the full calculation steps, not just the result. Checksumming the
trace proves that intermediate steps were not altered, which is required to demonstrate
a software logic error in a warranty dispute.

### Why attestation before issuance (not after)?

If attestation were an afterthought, users could claim data was verified retroactively.
By making attestation a prerequisite, the confirmation timestamp is before the issue
date, creating a clear audit trail.

### Why one certificate per snapshot?

CAM reconciliations are point-in-time calculations. Issuing multiple certificates for
the same snapshot would create ambiguity about which one is legally binding. The
`one_certificate_per_snapshot` UNIQUE constraint enforces this at the database level.

## Database Schema

```sql
-- reconciliation_snapshots (new columns)
engine_version VARCHAR(40)    -- Git SHA
trace_checksum VARCHAR(64)    -- SHA-256 of calculation trace

-- warranty_certificates (new table)
id                      UUID PRIMARY KEY
organization_id         UUID REFERENCES organizations
snapshot_id             UUID REFERENCES reconciliation_snapshots (UNIQUE)
status                  VARCHAR(30) CHECK (pending_attestation|eligible|issued|voided)
ingestion_batch_ids     UUID[]
data_attested_at        TIMESTAMPTZ
data_attested_by        UUID
certificate_number      VARCHAR(20) UNIQUE (WAR-YYYY-NNNNN)
issued_at               TIMESTAMPTZ
issued_by               UUID
voided_at               TIMESTAMPTZ
void_reason             TEXT
certificate_pdf_checksum VARCHAR(64)
```

RLS policies: members read their org's certificates; owners/admins can write.
