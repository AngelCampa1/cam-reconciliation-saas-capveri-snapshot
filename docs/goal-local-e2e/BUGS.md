### BUG-15 — unguarded `.data` on `maybe_single()` returns 500 instead of 404 (library design, prod-wide)
- Sev HIGH (correctness + UX + observability; a non-existent id returns a 500 stack trace instead of a clean 404; prod-affecting).
- Root cause (verified against installed source): in postgrest 2.28.0 `SyncMaybeSingleRequestBuilder.execute()` catches the "The result contains 0 rows" `APIError` and `return None` — so `<query>.maybe_single().execute()` is `None` (not an `APIResponse` with `data=None`) when nothing matches. The pin is `supabase>=2.10.0` (unbounded), so this is **not** local-only — prod hits the same library. NOTE: this is specific to `.maybe_single()`. A plain `.execute()` returns `.data == []` on 0 rows (empty list, falsy), so `if not result.data:` is SAFE there; the bug is only `maybe_single` + unguarded `.data`.

### BUG-03 — gross-up factor reported with inconsistent rounding mode
- Sev MED (correctness/auditability; reported factor, not the money total).
- File: `backend/app/services/calculation/gross_up_orchestrator.py:231`
  ```python
  # Quantize to 4 decimals to match calculate_gross_up_factor
  gross_up_factor = gross_up_factor.quantize(Decimal("0.0001"))   # <-- no rounding mode => ROUND_HALF_EVEN
  ```
  vs canonical `backend/app/services/calculation/gross_up.py:109`:
  ```python
  ... .quantize(Decimal("0.0001"), rounding=ROUND_HALF_UP)
  ```
- Why wrong: Python `Decimal.quantize` defaults to ROUND_HALF_EVEN. The two code paths can return different gross-up factors for exact-half cases at the 4th decimal, despite the comment asserting they match. CapVeri's value prop is defensible, reproducible numbers — a displayed factor that disagrees with the canonical helper is a correctness/consistency defect.
- Repro: target_occupancy / occupancy_rate landing on a value whose 5th decimal is exactly 5 with an even 4th digit (e.g. ...x5 half-way) rounds down under banker's, up under half-up.
- Fix: add `rounding=ROUND_HALF_UP` to line 231. One-liner, obviously correct. (Also LOWER-confidence candidates from the sweep — tenant_share.py:418 str() round-trip, occupancy.py intermediate non-quantization, fixed_cam_modeler.py:157 Decimal(str(int)) — judged masked-by-final-quantize / style; NOT logged as bugs.)

### BUG-14 — management-fee cap (`management_fee_percentage`) is extracted & stored but never enforced — FIXED
- Sev HIGH (financial-correctness gap: a contractual recovery cap that the engine silently ignored → potential over-recovery / landlord legal exposure). Status FIXED (deterministic Python cap; semantics confirmed from in-repo authority, not guessed).
- Root cause: `management_fee_percentage` flows through the whole pipeline EXCEPT the calculation:

  - Stored on the model (`models/lease_recovery_profile.py:94`: *"Management fee as decimal (e.g., 0.04 for 4%), distinct from admin fee. None when no management fee **cap** is found."* — the word "cap" is the key semantic hint).
  - Fetched into `LeaseTerms.management_fee_percentage` (`calculation/data_fetcher.py:215-218,276-278`) and listed in `_APPLICABLE_OVERRIDE_FIELDS` (`orchestrator.py:55`), and echoed by serialization/API.

  - `pools/auto_setup.py:75-80` maps GL descriptions `["management fee", "admin", "office expense"]` → an **operating-type "Management Fee" pool**, i.e. the management-fee dollars are GL-booked and recovered as ordinary operating expense. Combined with the "cap" docstring, this leans toward **cap-enforcement** semantics (limit recovery of the booked management-fee pool to X% of operating expenses) rather than an add-on charge — but this is not certain from code alone.
- Confirmed semantics (researched from in-repo authority, then user-confirmed — NOT guessed):
  - **Source of truth** = `extraction/prompts.py` field 8: `management_fee_percentage` is *"the property manager's fee **cap** expressed as a percentage of operating expenses"* (0–0.20), explicitly distinguished from `admin_fee_percentage` (an add-on/surcharge layered on top of the CAM total). So the field is a **cap on a GL-booked fee**, not an add-on.
  - **Cap base** = operating-type pools **excluding** the management-fee pool itself (net-of-fee). Confirmed by detection Rule 3 in `.claude/skills/capveri-business-context/references/detection-rules.md` (`permitted_fee = (total_expenses − billed_fee) × lease_rate # excludes fee from base`) and by the business-context "management fee circularity (fee calculated on a base that already includes the fee)" concern. Tax/insurance/capital are NOT in the base.
  - **Pool identification** = name-match within operating-type pools: `pools/auto_setup.py` names the booked-fee pool "Management Fee". The fix uses a lowercased substring marker `"management fee"`.
  - **Excess treatment** = non-recoverable; dropped from the property-level pool(s) **before** pro-rata so the capped fee flows naturally through exclusions/base-year/pro-rata/cap/admin/allocation.
- Fix (implemented in `calculation/tenant_share.py`): a "Step 0" before all tenant math. `_apply_management_fee_cap(...)` computes `operating_base = Σ operating-type pools excl. mgmt-fee pool(s)`, `cap = (rate × operating_base).quantize(0.01, HALF_UP)`, `booked_fee = Σ mgmt-fee pool(s)`; if `booked_fee > cap` it reduces the mgmt-fee pool(s) to exactly `cap` (pro-rata across multiple, last absorbs rounding) in both `pool_breakdown` and `original_pool_breakdown`, subtracts the excess from `total_recoverable_expenses`, and emits a `CalculationTrace` step. No-ops (with an explicit trace) when the rate is None/0, when `pool_types` is unavailable, or when no operating pool name contains "management fee". Never mutates inputs (returns adjusted copies).
- Tests: `TestManagementFeeCap` (6 tests) in `tests/test_tenant_share.py` — over-booked fee capped to net-of-fee base (40k booked, 4% of 160k → cap 6400, excess 33600 dropped, total 246400); fee within cap fully recoverable; None is a no-op; cap skipped when `pool_types` unavailable; cap skipped when no Management Fee pool present; cap composes with pro-rata (0.5 → 123200).
- Live evidence (scale harness, `Mgmt Fee Bldg`): the oracle was pinned to the BUGGY $280,000.00; with the cap enforced (operating non-fee 160k, mgmt-fee 40k, tax 80k, 4% cap → cap 6400, excess 33600 dropped) the corrected `total_recovery = $246,400.00`. `assert_known_total` and the `build_mgmt_fee_ignored` seed updated to model a distinct "Management Fee" operating pool (account 5300) so the harness exercises the real cap path.
- Follow-up (logged, not blocking): pool identification is **name-based** (`_MANAGEMENT_FEE_POOL_MARKER = "management fee"`). A custom/renamed fee pool won't be recognized and would silently skip the cap. Durable fix = add a pool subtype/flag (e.g. `is_management_fee`) on `expense_pools` set by `auto_setup.py`, and key the cap off that instead of the name.
