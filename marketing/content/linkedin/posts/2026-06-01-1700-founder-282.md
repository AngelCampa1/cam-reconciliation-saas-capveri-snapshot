GL exports contain per-tenant financial figures and negotiated lease terms. When a property manager sends that data to a third-party tool, four security questions determine whether the risk is acceptable.

This comes up in evaluations because the data involved is sensitive. GL exports contain financial figures tied to specific properties and tenants. Lease terms include negotiated rates, cap structures, and exclusion agreements that are confidential to the parties.

When a third-party tool touches this data, the security architecture matters. Here's what we've built at CapVeri and why each element exists.

Encryption in transit and at rest. Customer data is protected at both layers. This is the baseline. Any financial tool that handles sensitive records should be encrypting both the transmission and the stored data.

Row-level multi-tenant isolation. Every data table is partitioned by organization using PostgreSQL Row Level Security. This means One property management team's data cannot be accessed by another customer's session, even if both are on the same database infrastructure. The isolation is enforced at the database layer, not just the application layer.

Append-only audit log. Every change to GL entries, reconciliation snapshots, and lease data is captured with before/after state and a timestamp. This is relevant for financial recordkeeping: if a question arises about what a calculation used as input at a specific point in time, the log has the answer.

AI with mandatory human review. AI is used to extract lease terms from PDFs. Every extraction requires a human reviewer to confirm or correct before it affects any calculation. The AI output does not flow directly into financial records.

These aren't marketing claims. They're the architectural decisions that allow a property manager or CFO to demonstrate due diligence to their own stakeholders when they bring in a new financial operations tool.
